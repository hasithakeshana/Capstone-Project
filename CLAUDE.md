# LearnLab

## Project overview

LearnLab is a lightweight learning management system: course catalog, enrollment, lessons, progress tracking, and auto-graded MCQ and TRUE/FALSE quizzes. Three roles: learner, instructor, admin. Internal tool, run locally.
Business context: [docs/business-case.md](docs/business-case.md). Full spec: [specs/app_spec.md](specs/app_spec.md).

## Project rules

- **No hand-coding:** all production code, tests and migrations are generated by Claude Code agents. Hand edits are limited to specs, CLAUDE.md, agents, hooks, skills and other substrate files.
- **Spec-Is-Truth:** if a spec and the code disagree, the spec wins. Change the spec first with `/spec-change`, then regenerate the code.
- **PR-only merge:** no direct commits to `main`. All changes go through reviewed pull requests.
- **Synthetic data:** use only dummy data: fake names and `@example.com` emails.

## Commands

Backend (from repo root):
- `uv run pytest -x -q` — tests
- `uv run ruff check --fix .` — lint
- `uv run mypy src/` — types
- `uv run lint-imports` — layer rules
- `uv run pytest --cov=src --cov-report=xml:reports/coverage.xml` — coverage

Frontend (from `frontend/`):
- `npm test` — tests
- `npm run lint` — lint
- `npm run build` — build
- `npm test -- --coverage` — coverage (writes `reports/lcov.info`)

Run the app: one command, defined in the sprint 1 design.
E2E (Playwright): `npx playwright test`

## Project layout

- `src/` — backend (FastAPI): controllers, services, repositories, domain, core
- `tests/` — backend tests (domain, controllers, services, repositories, architecture)
- `migrations/` — Alembic migrations (append-only)
- `frontend/` — React + Vite + TypeScript + Tailwind app
- `e2e/` — Playwright tests and screenshot snapshots
- `specs/` — app spec, feature specs, sprint PRDs, design constitution and glossary
- `docs/` — business case, architecture, TDD, post-mortems

## Architecture

Layers: controllers → services → repositories → domain (+ core for config and logging). Imports flow one way only. See [docs/architecture.md](docs/architecture.md) and [specs/design/constitution.md](specs/design/constitution.md).

## Testing

- Every AC has at least one test. Every test carries the literal id AC-NN (see process rule PR-learnlab-03): pytest `test_acNN_<behaviour>` + `@pytest.mark.ac("AC-NN")` + docstring `"AC-NN (E1-S1-ACn): …"`; Vitest/Playwright titles `"AC-NN (E1-S1-ACn): …"`.
- At least 20 unit tests. Coverage ≥ 80%, written to `reports/` (`coverage.xml`, `lcov.info`).
- Playwright UI tests end with a screenshot assertion; snapshots are committed.
- Red → green → refactor for every AC. See [docs/tdd.md](docs/tdd.md).

## Git & PR workflow

- **Branches:** one per step or sprint, cut from an up-to-date `main`: `chore/foundation`, `sprint-N/<name>`, `fix/<name>`, `docs/<name>`. Never commit or push to `main`.
- **Commits:** made by agents. Per AC: `test(AC-NN): …` → `feat(AC-NN): …` → `refactor(AC-NN): …`. Every message ends with `Co-Authored-By: Claude <noreply@anthropic.com>`.
- **Pull requests:** push the branch, then open a PR to `main` with `gh pr create`. The PR description is the output of `node .claude/scripts/pr-body.js --require-gate`.
- **Merge:** only after CI is green and, when the Claude review ran, its comment is read. A human merges with a merge commit (no squash, no rebase, no fast-forward), then deletes the branch.
- The harness's local `auto/group-*` branches are never pushed.

## Review checklist

Every Claude review (CI) checks:
- Code that does not match its spec, or a spec change with no matching code change.
- An AC with no test that contains its id.
- Layer violations against controllers → services → repositories → domain.
- Role checks missing on a controller route (except `/health`, register, login).
- Learner PII in logs (NFR-03).
- Edits or deletes on append-only records (attempts, completions, enrollments), or edits to an existing migration.
- Quiz scores that use floating-point math.
- Security issues: injection, auth bypass, hardcoded secrets.
- Breaks of the project rules above.

### Large codebase navigation

- Claude Code respects `.gitignore` for file navigation — keep it comprehensive
- Before broad source reads, check `specs/brownfield/wiki/WIKI.md` and `specs/brownfield/symbol-map.md`; if the wiki is a placeholder, use `specs/design/component-map.md` until source exists

- For monorepos, add subdirectory CLAUDE.md files with scoped test/lint commands
- Install recommended LSP servers (see "LSP integration" above) for symbol-level navigation

- State files are auto-archived when they grow large — see `.claude/scripts/archive-state.js`
- Run `node .claude/scripts/archive-state.js` periodically in long-running projects

### Code style

- For existing codebases, run `/brownfield` before broad planning or refactoring
- Small new projects (CLI tools, single-script utilities, small libraries) should use `/build --lite` instead of `/brd → /spec → /design`; see `.claude/skills/build/references/lite-lane.md`
- Small low-risk fixes may use `/vibe` instead of the full SDLC pipeline; see `.claude/skills/vibe/SKILL.md`
- TDD mandatory: test first, then implement
- 100% meaningful coverage target, 80% floor
- Functions ≤ 30 lines, files ≤ 300 lines (enforced by pre-write-gate)
- Static typing everywhere (zero `any`)
- See `.claude/skills/code-gen/SKILL.md` for full rules
